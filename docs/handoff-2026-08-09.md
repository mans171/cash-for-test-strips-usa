# CFTS Handoff — 2026-08-09

## What this is

Cash For Test Strips USA — a Next.js directory site at https://cash4teststripsusa.com that connects people selling unused diabetic test strips with local cash buyers. This handoff covers a long multi-day session that added real Supabase-Auth accounts across the whole site, redesigned `/sell`'s checkout, fixed several real bugs, and left a large new feature (buyer accounts / listing claims) designed but not yet built.

Supabase project ref: `whgwneuarnrsktolmqdj`. Vercel project: `cash-for-test-strips-usa` in team `mans171s-projects`. Repo: `mans171/cash-for-test-strips-usa`, deploys on every push to `main`.

## What was built this session (chronological, see `git log` for exact commits)

1. **Auth foundation** — Supabase Auth (email+password, no email verification), `profiles` table (`role: 'customer' | 'buyer'`), `lib/auth.ts`/`lib/auth-client.tsx`, `/signup`/`/login` pages, `proxy.ts` (Next 16 renamed `middleware.ts`) for session refresh.
2. **Customer accounts on `/sell`** — gated buyer contact behind login, then (see #6) removed that gate entirely in favor of folding account creation into checkout itself.
3. **Server-side buyer email** — when a seller submits contact info, the buyer gets emailed automatically (with the owner CC'd) instead of relying on the seller to manually text/email. `lib/email.ts`, `lib/order-matching.ts`'s `getCompanyContact`.
4. **Text Now + order summary** — customer-initiated SMS option alongside the automatic email, plus an order summary on the confirmation screen.
5. **Directory gating + nav login state** — `/directory` and `/company/[slug]` gate Contact/Visit-site buttons behind login; `SiteNav` shows login/logout state.
6. **Sell account-first checkout** — the big redesign. `/sell` no longer shows a buyer-results screen with a gate bolted on afterward. Flow is now: build order → submit → if anonymous, ONE combined account form (name/phone/email/password/city/state, "Create your account" button, zero buyer info visible) → submitting creates the account and immediately shows unlocked results. Already-logged-in customers skip straight to results. A "Log in instead" toggle exists for returning-but-not-logged-in customers (added after final review caught that the redesign had silently dropped this path). See `app/sell/SellFlowClient.tsx` — this file is now the center of gravity for the whole checkout flow.
7. **UI polish pass** — brought `/sell` in line with the rest of the site's card/button styling (it had drifted to plain flat boxes), added a 3-step progress indicator, fixed product-photo tiles that were technically rendering but invisible (white packaging on white cards).
8. **Fixed a session-long flaky test** — `app/api/submissions` and `app/api/admin/review` tests intermittently timed out. Root cause: `createSubmission()` awaited a real Gmail SMTP send that already swallows its own errors, so the await bought nothing but exposure to network latency. Mocked `sendEmail` in those two test files.
9. **Production email latency + error-leak fixes** — `lib/submissions.ts`'s three notification-email sends now use Next's `after()` instead of blocking the response. `/sell`'s account form no longer surfaces raw Supabase/Postgres error text to customers (a profile-insert RLS error now logs server-side and shows a generic message; a duplicate-email signup gets a specific "log in instead" nudge).
10. **Real security fix: buyer contact info now actually gated, not just hidden.** `/directory` and `/company/[slug]` were embedding real phone/email/URL into the server-rendered HTML for every visitor regardless of login state — `RequiresAccount` only hid it with CSS afterward, so `curl`/view-source could read every buyer's contact info with no account. Fixed at the source: both pages check auth server-side and strip contact fields before rendering (`lib/company-contact.ts`, shared with `/api/sell/match`). `RequiresAccount` had no remaining callers after this and was deleted.
11. **Account-form a11y + retry polish** — real `<label>` elements on every account-stage field, a "Try again" recovery when the buyer-match fetch fails right after account creation (shared by signup/profile-retry/login), password cleared from state once no longer needed and on "back" navigation.
12. **Forgot-password flow for customer accounts** — `/forgot-password` + `/reset-password`, using Supabase Auth's own `resetPasswordForEmail`/`updateUser` (not the admin panel's separate bespoke token system, since customers are real Supabase Auth users). Linked from `LoginForm`.
13. **Expiration date UX** — selecting a product on `/sell` now prefills expiration to 9 months out immediately, and every option in the dropdown shows the actual calendar month (e.g. "9 months (May 2027)") instead of a bare count. `lib/expiration.ts`'s `EXPIRATION_MONTH_OPTIONS` became a function, `getExpirationMonthOptions(today)`, since a calendar label can't be a static list.

## In progress, NOT yet built: buyer accounts / listing claims

This was being designed when the session ended — full research is done, two key decisions are locked in, but **no spec file has been written yet** and no code exists. See "Prompt for next session" below.

### Current state (as of this session)

- `/buyer` (`app/buyer/BuyerPortalClient.tsx`) is a fully anonymous, phone-number-lookup flow: type a phone → 0 matches → new-listing form; 1 match → edit form; 2+ matches → pick one. No account, no session, no claim token. The only ownership check is `createSubmission()` re-verifying the submitted phone matches the target company's phone on file.
- `companies` has **no ownership column at all** — no `claimed_by`, no FK to `auth.users` or `profiles`.
- `profiles` already supports `role = 'buyer'`, and `SignupForm.tsx` already accepts a `role` prop, but nothing currently uses `role="buyer"` anywhere, and `profiles` has no link to `companies`.
- `submissions` (schema, RLS, `lib/submissions.ts`'s `createSubmission`/`approveSubmission`/`rejectSubmission`) and the admin dashboard's Submissions tab (`app/admin/AdminDashboardClient.tsx`) are the existing review/approval machinery this new feature should build on top of, not replace.
- Admin auth is a separate bespoke system (`lib/admin-auth.ts`, shared password + signed cookie), unrelated to Supabase Auth.

### Decisions already made (confirmed this session, some carried from an earlier session)

- Claims require **manual admin approval** via a new "Claims" tab in the existing admin dashboard — not automatic on phone-number match.
- Claiming and editing are **two separate steps**: claim first (identity-only, no content change), admin approves, *then* the buyer can log in and submit content edits through the **existing Submissions review flow** (not a new review mechanism).
- A brand-new buyer listing (no existing company to claim) also requires an account — its first submission gets auto-created **and auto-claimed** by that buyer on admin approval.
- The new account-based flow **fully replaces** `/buyer`'s current anonymous phone-lookup flow — the old form goes away entirely.
- A buyer account **can claim/own multiple companies** (e.g. a franchise with several locations) — this is more schema/UI work than a one-company-per-account model, so the data model needs to support a `claims`-style join rather than a single `claimed_by` column being sufficient on its own... actually re-examine: a many-to-many needs either a join table or (simpler) just letting `companies.claimed_by` be a single FK per company (many companies can point to the same user — that's already many-to-many from the user's side) — a dedicated `claims` table (see below) naturally supports this without extra modeling.

### Design sketch (not yet finalized into a spec — needs a fresh brainstorming pass)

- New `claims` table: `id, company_id (FK companies, not null), user_id (FK auth.users, not null), submitted_phone, status ('pending'|'approved'|'rejected'), created_at, reviewed_at`. Locked-down RLS like `submissions` (no anon read/write; all access via `supabaseAdmin` from server routes).
- `companies` gains `claimed_by uuid references auth.users(id)` (nullable). Since a `claims` table already models the relationship, whether `claimed_by` is still needed as a denormalized column on `companies` (fast lookup) vs. derived from `claims` where `status = 'approved'` is an open implementation question.
- `submissions` gains `submitted_by_user_id uuid references auth.users(id)` (nullable, set only when the submitter was authenticated) — lets `approveSubmission` auto-claim a new company to its submitter, and lets `createSubmission` relax/skip the phone-match check for edits from an already-claimed owner.
- New buyer-facing pages under `/buyer`: account creation/login (reuse `SignupForm role="buyer"` / `LoginForm`), a claim-search UI, a "My Listings" dashboard (plural, since multi-company is in scope), an edit form per listing (submits through the existing `/api/submissions` flow).
- New admin "Claims" tab, parallel to the existing Submissions tab, with the same diff-style review UX.
- New API routes needed: `POST /api/claims` (authenticated, create a pending claim), a way for a buyer to fetch their own claimed companies + pending claim status, `POST /api/admin/claims/review` (admin-authenticated approve/reject), and `/api/admin/data` extended to include pending claims.

## Important technical notes for whoever picks this up

- **Push immediately after every merge, verify via `vercel list --yes` or the Vercel dashboard.** Several times this session, work sat merged-but-unpushed and the live site silently ran stale code. There is no reliable Vercel MCP tool for this project (403/404) — use the CLI (`vercel list --yes`) or direct dashboard navigation.
- **Live-DB integration tests are the norm here**, not mocks — `npm test` hits the real Supabase project. Mocks are the rare exception (real SMTP sends, real Next.js request-scope-dependent APIs like `after()`, `createServerSupabaseClient()`'s `cookies()` — all things that can't exist when a route handler is invoked directly in a unit test). A test file's own comments explain why each mock exists; follow that precedent rather than mocking broadly.
- **A 2-8 file live-DB test flake can happen from real Supabase network blips**, distinct from the SMTP-blocking flake that was root-caused and fixed this session — if `npm test` fails oddly, re-run before assuming a regression.
- **Any manual verification that touches the live database must clean up after itself** — this session repeatedly created throwaway test accounts/companies/submissions directly against production Supabase and deleted them via `supabaseAdmin` afterward, verifying zero stray rows remained. Never leave test data live, and never test against a real production buyer (one earlier session accidentally sent a real email to a real buyer during testing — always use synthetic data).
- **Buyer contact info (email/phone/url) must always be resolved/stripped server-side**, never trust client-supplied buyer contact data, and never assume hiding something with CSS/JS is the same as not sending it to the client at all — this was the exact bug fixed in item #10 above.
- **`RequiresAccount` no longer exists** — it was deleted after its last two callers (`/directory`, `/company/[slug]`) were migrated to server-side auth checks. Don't recreate the old client-side-only gating pattern for anything server-renderable.
- **Next.js 16 renamed `middleware.ts` → `proxy.ts`** (exported function `middleware` → `proxy`) — a leftover `middleware.ts` is silently ignored with no error, and this is load-bearing for the whole session cookie refresh.
- **`sendEmail()` (best-effort, swallows its own errors) vs `sendEmailOrThrow()`** — two different functions in `lib/email.ts` for two different intents. Best-effort notification sends should use `after()` so they never block a response; sends whose success actually matters to the caller use the throwing variant and get awaited.
